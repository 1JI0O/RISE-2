## Goal

Implement a train-only experimental variant that removes gripper/arm points from the 3D cloud and injects a synthetic TCP anchor, without modifying existing files in place. First produce visualization artifacts (mask overlay + point cloud) to validate the design, then prepare a 4-GPU training path on GPUs `4,5,6,7`.

## Repo facts confirmed

- Training currently uses `train.py` + `dataset/realworld.py` via `command_train_single_foar_purplebox.sh` and `configs/single_foar_purplebox.yaml`.
- The current mask-aware path already zeroes masked depth before point-cloud creation in `dataset/realworld.py:528`.
- Dataset samples return point coordinates as xyz features (`cloud_feats` is just `points.astype(np.float32)`), so adding a synthetic point is straightforward at dataset level before voxelization.
- The raw arm mask example `/data/haoxiang/data/zihao_foar2/flip_0326_purple_box_masks_raw/scene_0001/cam_104422070117/arm/00007.png` is a binary `L` image with values `{0,255}`.
- The single-arm lowdim file stores TCP pose directly: `lowdim_dict["robot"][0:7]` is the camera-base-frame TCP pose in quaternion form, and `lowdim_dict["gripper"]` stores widths/commands. This means the synthetic TCP anchor can be generated from lowdim alone; no IK/joint reconstruction is needed for the train path.

## Recommended design

Use a small synthetic TCP point cluster instead of one isolated point.

- Reason: a single point is likely too fragile after voxelization, sparse conv downsampling, and augmentation.
- Recommended default: inject `7` points centered at TCP with offsets `[(0,0,0), (+r,0,0), (-r,0,0), (0,+r,0), (0,-r,0), (0,0,+r), (0,0,-r)]`.
- Recommended radius: `r = 0.75 * voxel_size` so neighboring offsets are likely to survive discretization without spreading too far.
- Important correction: the relevant "weight" here is not diffusion/action loss weighting. In this repo, `image_mask_weight` participates in `SpatialAligner -> WeightedSpatialInterpolation` as per-patch source weights during 2D-patch to 3D-point interpolation (`policy/policy.py:74`, `policy/sparse_modules.py:210`). So the TCP-anchor design should consider whether nearby image patches should receive extra interpolation weight, not just whether the anchor survives geometrically.
- Recommended feature value: keep feature semantics consistent with the existing cloud by using the injected xyz coordinates themselves as `cloud_feats`.
- Recommended augmentation behavior: inject the TCP cluster before the existing point augmentation so it transforms consistently with the rest of the cloud and with action TCPs.

## Patch-weight handling options for the TCP region

This needs to be explicit because the current training path computes:

- `mask_ratio = image_processor.image_coord_pooling(mask01_t)` in the dataset;
- `image_mask_weight = 1 - mask_ratio`;
- then passes that into interpolation as `src_weights`, which directly downweights image tokens whose patches are heavily masked.

If we remove the full arm/gripper from the cloud but also keep heavily downweighting the corresponding image patches, the model may lose almost all signal around the TCP region. The synthetic TCP anchor would still exist in 3D, but its image-conditioned feature interpolation may be weak exactly where we care most.

Recommended options:

1. `anchor_only` (recommended first try)
   - Keep arm removal in 3D.
   - Keep the normal arm mask for most patches.
   - But for patches near projected TCP, override `image_mask_weight` upward to a floor value, i.e. `max(weight, tcp_patch_weight_floor)`.
   - Updated default: TCP neighborhood radius `1` patch in pooled patch space, weight floor `1.0` so the local TCP neighborhood is not downweighted at all.
   - Reason: preserves the existing mask-aware behavior globally while preventing the TCP neighborhood from being treated as fully untrusted.

2. `anchor_disk`
   - Build a small 2D disk around projected TCP in image space before pooling.
   - Mark that disk as trusted in the weight map even if the arm mask says untrusted.
   - This is slightly more spatially precise than patch-space override, but needs extra resize/projection care.

3. `no_2d_downweight_for_arm`
   - Use arm mask only for 3D removal, but do not feed that arm mask into `image_mask_weight` at all.
   - Simpler, but may reintroduce undesirable image influence from the rest of the arm region.

4. `full_downweight`
   - Remove arm in 3D and keep the current full patch downweighting unchanged.
   - Safest in terms of preserving mask-aware semantics, but likely too suppressive near TCP.

## Updated recommendation

Use a hybrid policy:

- Remove arm/gripper points from the point cloud using the aligned arm mask.
- Inject a small TCP anchor cluster in 3D.
- For `image_mask_weight`, keep arm-mask downweighting globally, but force the projected TCP neighborhood back to weight `1.0`.

This gives the model:

- explicit 3D evidence at TCP;
- reduced contamination from arm/gripper geometry;
- some surviving 2D image contribution near TCP during interpolation.

## Patch-grid size and area intuition

For the current single-arm FOAR purple-box training config:

- `configs/single_foar_purplebox.yaml` uses `img_size_dinov2: [252, 448]`
- and `img_coord_size_dinov2: [18, 32]`

So one training image is pooled into:

- `18 x 32 = 576` patch tokens total

This means:

- `tcp_patch_radius = 0` restores exactly `1` patch, i.e. about `0.17%` of all image patches
- `tcp_patch_radius = 1` restores up to `3 x 3 = 9` patches, i.e. about `1.56%` of all image patches

In resized-image pixel terms:

- each patch is roughly `252/18 = 14` by `448/32 = 14` pixels
- a `3 x 3` patch neighborhood is roughly `42 x 42` pixels in the resized image

Interpretation:

- `radius = 1` is still globally small, but may re-enable a bit of nearby gripper/arm appearance if TCP is visually adjacent to the arm body
- `radius = 0` is the most conservative version and may be preferable if the goal is to preserve only the TCP center patch

## Current tradeoff recommendation

Because the user explicitly raised concern that `3 x 3` may include too much visual content, the implementation should keep both options easy to switch and likely start with one of these two ablations:

1. conservative: `tcp_patch_radius = 0`, `tcp_patch_weight_floor = 1.0`
2. robust: `tcp_patch_radius = 1`, `tcp_patch_weight_floor = 1.0`

The visual inspection stage should compare both before long training.

Updated user preference:

- use `tcp_patch_radius = 1`
- use `tcp_patch_weight_floor = 1.0`

## Which TCP location should drive patch-weight restoration?

The restored patch neighborhood should be centered on the true TCP center projection only, not on all 7 injected anchor points.

Reasoning:

- the 7 injected 3D points are only a geometric support trick to help the TCP anchor survive voxelization / sparse downsampling;
- they are not 7 distinct semantic keypoints;
- if all 7 synthetic offsets are separately projected into image space and each restores patch weights, the effective restored image area can become unintentionally larger and more anisotropic;
- patch-weight restoration is meant to preserve image guidance near the single semantic TCP location.

Implementation rule:

1. Compute the camera-frame TCP center xyz.
2. Project that center once to image / patch coordinates.
3. Use that single projected center to define the restored patch neighborhood (`radius = 1`).
4. Inject the 7-point 3D anchor cluster independently for the point cloud.

So the 3D anchor uses 7 points, but the 2D patch-weight override uses one center location.

## Implementation details for patch weighting in the copied dataset

After computing the observation TCP in camera coordinates:

1. Project TCP xyz to image pixel coordinates using camera intrinsics / depth geometry already available in the sample.
2. Convert that location into pooled patch coordinates matching `image_mask_weight` resolution.
3. After the normal `mask_ratio -> image_mask_weight = 1 - mask_ratio` step, overwrite the local TCP patch neighborhood with `max(current_weight, tcp_patch_weight_floor)`.
4. Keep the existing 3-value interpolation stability tail unchanged.
